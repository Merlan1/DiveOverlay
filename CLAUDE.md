# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DiveOverlay overlays dive-computer CSV telemetry (depth, temperature, pressure, heart rate, elapsed dive time) onto video. It was originally a Python/OpenCV script and is now a Rust workspace that shells out to `ffmpeg`/`ffprobe` (no OpenCV/libav linking). All user-facing strings (CLI help, error messages, GUI labels) are in English.

## Commands

```bash
cargo build --release                 # binaries land in target/release/dive_overlay_cli(.exe) / dive_overlay_gui(.exe)
cargo test --workspace                # full suite
cargo test -p dive_overlay_core sync:: # run one module's tests, e.g. sync, csv_data, overlay, pipeline
cargo test some_test_name              # run a single test by name (any crate)
cargo run --release --bin dive_overlay_gui
cargo run --release --bin dive_overlay_cli -- --csv dive.csv --video input.mp4 --video-sync-sec 3.2 --csv-sync-mmss 0:10
```

Requires `ffmpeg`/`ffprobe` on PATH. Many tests in `dive_overlay_core` (pipeline, sync) synthesize clips at runtime via `ffmpeg -f lavfi` and a couple hit the real GitHub API (marked `#[ignore]`) — they need working `ffmpeg` to pass.

## Workspace layout

- `crates/dive_overlay_core` — all domain logic: CSV parsing, sample lookup, overlay drawing, ffprobe wrapper, ffmpeg pipeline, subtitle generation, multi-clip/auto-sync. CLI and GUI are both thin shells over this crate; new dive-processing logic belongs here, not duplicated in either frontend.
- `crates/dive_overlay_cli` — clap-based CLI binary.
- `crates/dive_overlay_gui` — egui/eframe GUI binary.

## Core module map (`dive_overlay_core/src`)

- `model.rs` — `DiveSample`, `ClipJob`, `Field` enum (`Time`/`Depth`/`Temp`/`Pressure`/`Hr`), and `value_for_field` (the overlay display strings, e.g. `"Depth: {:.1} m"`).
- `csv_data.rs` — flexible CSV loading: `find_column_index` does a two-phase match (exact match over candidates first, then substring) ported verbatim from the original Python's `find_column`, including iteration order — this is load-bearing for ambiguous headers, don't "clean it up". Also owns `mm:ss`/`hh:mm:ss` duration parsing/formatting and `--column-map` parsing. `read_csv_datetime_columns`/`read_first_row_columns` (and the `date=`/`clock=` map keys) are no longer used by auto-sync, which reads its deltas from the video files alone; they remain as public API.
- `lookup.rs` — `choose_sample_index`: finds the latest sample at-or-before a given dive-elapsed-second (last-known-value-carried-forward semantics), a `partition_point`-based port of Python's `bisect.bisect_right(...) - 1`.
- `overlay.rs` — `build_overlay_lines` (shared by CLI burned-in overlay, GUI preview, and SRT generation — keeps all three visually identical), pixel drawing (`draw_overlay`, `draw_depth_graph`) via `imageproc`/`ab_glyph`, using a bundled `DejaVuSans.ttf`. Every drawn size — both fonts, padding, label insets, stroke width — must come from `OverlayMetrics`/`GraphMetrics`, never a literal pixel count: they scale off `line_height_for(height)` so the overlay is the same fraction of the picture at any resolution. The sizes were hand-tuned at 1080p and the factor is 1.0 there by construction, so that rendering stays pixel-identical (pinned by `metrics_at_1080p_match_the_hand_tuned_originals`). Both fonts have a floor for small frames, where strict proportionality would go sub-readable. Adding a hard-coded size here is the bug that made 5.3K footage draw 22px glyphs inside a 134px line. `plan_graph` plots the dive from elapsed zero to the current second — the whole profile so far, not a trailing window — so the box holds more seconds as the dive runs and its horizontal resolution drops accordingly; that is the intent. The depth axis auto-ranges over the plotted span, so it grows monotonically instead of rescaling as a window slid. Drawing is split from planning on purpose: a `GraphPlan` (quantized polyline, labels, metrics, placement) is everything `render_graph_tile` reads, so it doubles as an exact cache key, and consecutive samples landing on one pixel are dropped so the segment count is bounded by the box rather than the dive length. The plot’s right edge is snapped down to a whole second — the rate dive computers log at and the rate the info box counts at. Without that snap the horizontal scale creeps every frame and, across hundreds of points, a few always cross a rounding boundary, which misses the cache on nearly every frame while changing nothing visible.
  Every overlay element — the info box and the depth graph alike — is rendered into a standalone RGBA tile with its translucency baked into the alpha channel, and the frame is only ever touched by a composite. That is what lets one set of drawing code serve both a packed-RGB frame (the GUI's sync preview, via `composite_tile`) and a planar YUV frame (the pipeline, via `composite_tile_yuv`): supporting a pixel format means writing one composite function, not a variant of every drawing primitive. `YuvTile::from_rgba` converts a tile once into the planes and resolutions a 4:2:0 blend needs, and `OverlayCache` keeps that conversion alongside the RGBA tile, so the per-frame cost is a pure blend — the info box only re-renders when its text changes, about once a second. It holds a second, independently keyed slot for the depth graph (`CachedGraph`, keyed on the whole `GraphPlan`), on the same terms: at 30 fps the graph re-renders and re-converts once a second instead of 30 times. Tile placement is rounded to even coordinates (`align_to_chroma_grid`), or a tile's chroma would straddle the frame's 2x2 blocks and bleed outside its own edges. The palette is deliberately all greys: a neutral colour is `U = V = 128` in every YUV matrix, so nothing depends on correctly detecting BT.601 vs BT.709, and a thin saturated line (the depth curve was cyan) aliases badly once its chroma is stored at half resolution.
- `subtitle.rs` — `build_srt`: renders one SRT cue per second, reusing `build_overlay_lines` so subtitle-mode text matches overlay-mode text exactly. `concat_srt` is the inverse-ish partner used by merging: it re-parses rendered cues, shifts them by a per-part offset and renumbers them onto a joined timeline.
- `merge.rs` — combining one dive's clips into a single output. `plan_merge` sorts jobs by `dive_start_sec` (`csv_sync_sec - video_sync_sec`, valid in both sync modes) and redirects each job's `output_path` to a numbered scratch part; `finish_merge` concatenates, rebuilds the subtitle sidecar and deletes the parts. The concat demuxer call maps streams explicitly (`0:v:0`, `0:a:0?`, `0:s:0?`), never `-map 0`: real camera footage carries a `tmcd` timecode track that survives a `-c copy` remux, and mapping it fails the merge with "Cannot map stream #0:3 - unsupported type". `merge_clips` prefers the lossless concat demuxer (`-c copy`) and falls back to a re-encoding concat filter when clips differ in resolution/fps/audio — except in subtitle mode, which errors instead, since re-encoding would defeat that mode. Clips are joined back-to-back with no gap filler on purpose (the overlay's dive time visibly jumps at each seam). Parts are deliberately *not* deleted on failure or cancellation, so the expensive per-clip encodes survive. The concat runs entirely inside one ffmpeg call, so the only position information available comes from `-progress pipe:1` on its stdout (`spawn_progress_reader` parses `out_time_us`); `merge_clips`/`finish_merge` forward it as `(done_sec, total_sec)` to a caller callback, which is what feeds the CLI's `Combining` line and the GUI's bar during a multi-minute merge.
- `pipeline.rs` — the two processing paths:
  - `process_clip` (overlay mode): spawns an ffmpeg decoder (raw planar 4:2:0 to stdout) and encoder (the same on stdin, muxes original audio via `-map 1:a:0?`, so audio-less inputs don't fail) as subprocesses connected through this process; the overlay is composited into the planes between decode and encode. Both ends use the source's own colour range (`ColorRange::raw_pixel_format`), so the decoder converts nothing and full-range footage still gets exactly the one range conversion at encode time that it always did.
  - `OutputResolution` (`--resolution` / GUI dropdown: original, 4k, 1080p, 720p) downscales the output. It only ever scales *down* (picking 4K for 1080p footage is a no-op, not an upscale), fits the picture inside the target box preserving aspect ratio, orients that box to the source so portrait footage isn't squashed, and rounds both dimensions to even for yuv420p. The scale is applied **in the decoder** (`spawn_decoder`'s `scale_to`), not the encoder, and that placement is the point: it shrinks the encode, the pipe traffic (23.8 MB → 12.4 MB per planar frame going from 5.3K to 4K) and the draw area at once, where an encoder-side filter would shrink only the encode. It also feeds `resolve_encoder`, so a 5.3K job that had no hardware path (5312 busts every hardware encoder's 4096 per-axis cap) silently gains one at 4K. The target size is computed in Rust and passed to ffmpeg as an explicit `scale=W:H` rather than a filter expression, because the read buffer is sized from the same two numbers and a disagreement would desynchronize the raw stream instead of failing loudly. 4:2:0 cannot represent an odd width or height, so `process_clip` rejects an odd frame size outright, with a message pointing at `--resolution`. Ignored in subtitle mode, which re-muxes losslessly.
  - **Performance profile** (measured on `test_clip0.MP4`, 210 frames, 12 cores; see `TODO.md` for the history). Whole-program: 4.52 fps at the defaults (5.3K, libx264 veryfast), 14.60 at `--resolution 4k --hw-accel`, 21.87 at 1080p. At 5.3K the encoder dominates outright; at 4K with a hardware encoder what remains is the HEVC decode and the single-threaded frame loop, since `process_clip` serializes read → draw → write on one thread. Drawing is only ~6% of runtime and `--show-graph` ~1% — at those defaults, where the encoder dominates. `--show-graph` is not free everywhere: on `test_clip0.MP4` at `--resolution 4k --hw-accel` the uncached graph cost ~9% of whole-program time (82 s with the graph vs ~75 s without, interleaved runs), because it re-rendered the tile and re-converted a 1228x583 RGBA tile to YUV on every frame. With `CachedGraph` that drops into the noise (69-77 s with the graph vs 73-77 s without). Interleave before/after runs and repeat them: single runs on this machine varied by ~25%. Benchmark encoders on `test_clip0.MP4`, never on `lavfi` sources: x264's speed collapses on real content while fixed-function encoders barely move, so synthetic clips rank them backwards (libx264 veryfast measured 18.0 fps synthetic vs 5.7 fps real).
  - `process_clip_subtitles` (subtitle mode): no decode/encode loop — writes an SRT sidecar file and remuxes losslessly (`-c copy` video/audio, `mov_text` subtitle stream), since no pixels are touched.
  - `extract_frame_at`: two-tier seek (fast input-side `-ss`, falling back to frame-accurate output-side `-ss`) for the GUI's sync preview.
  - `probe_hw_encoder` must run at the *job's* frame size (it takes `width`/`height` and `resolve_encoder` passes them through). A hardware encoder's maximum resolution is a property of the silicon, and it clamps each *dimension* independently rather than capping total pixels: the dev machine's `h264_amf` encodes 4096x4096 (16.8 MP) but refuses 4608x2592 (11.9 MP) with `encoder->Init() failed with error 5`, since 4608 is past its per-axis maximum of 4096. Probing at a fixed small size reported "available" and then failed the whole job on 5.3K GoPro footage, which busts that limit on width alone. Results are memoized per `(encoder, width, height)` so a multi-clip run probes once.
  - Encoder stdin must be dropped (not just left to `Drop`) before `wait()`, otherwise ffmpeg never sees EOF and hangs without finalizing the mp4.
  - Frames go to the encoder through `write_frame`, in 256 KiB chunks. A single `write_all` of a whole large frame (a 5.3K rgb24 frame was ~48 MB; planar 4:2:0 halved that, but the hazard is unchanged) into the stdin pipe fails partway through a full-length dive on Windows with `ERROR_NO_SYSTEM_RESOURCES` (os error 1450) — one write large enough to exhaust the non-paged pool. Chunk writes retry that error and `EINTR` with a backoff; every other write error is still a dead encoder.
- `ffprobe.rs` — `probe_video` (width/height/fps/estimated_frames/duration/creation_time/timecode via `ffprobe -show_streams -show_format`). `timecode_sec` is the `tmcd` start timecode as seconds since local midnight, parsed at the *nominal* frame rate (`fps.round()`, so 30 for 30000/1001): drop-frame only governs how a timecode advances *through* a clip, and each clip's start value is stamped fresh from the camera's clock, so no 1000/1001 correction applies. `00:00:00:00` reads as `None` — that is what an unset camera clock writes, and taking it as midnight would place the clip 12 hours from every real timecode. `width`/`height` are the *decoded* frame dimensions: they're swapped for ±90° `Display Matrix` rotation tags because ffmpeg auto-rotates on decode, and `fps` prefers `avg_frame_rate` over `r_frame_rate` (which overstates the rate for variable-frame-rate sources). The decoder in `pipeline.rs` runs `-fps_mode cfr -r <fps>` so `frame_idx / fps` is a valid timestamp; don't switch it back to `passthrough`. and `ensure_ffmpeg_available` (fails fast with a clear message if `ffmpeg`/`ffprobe` aren't on PATH, instead of every downstream `Command::spawn` failing with an opaque ENOENT). `estimated_frames` is a rough estimate (from `nb_frames`, falling back to duration×fps) — fine for progress bars, never usable as a decode-loop termination condition.
- `sync.rs` — `parse_clip_spec` (`video|video_sync_sec|csv_sync_mmss[|output]`) and `compute_auto_sync`: derives each clip's `csv_sync_sec` by offsetting the base clip's *own* hand-entered `csv_sync_sec` by how much later the clip started recording. Nothing wall-clock is read from the CSV — a delta between two clips of one camera needs no shared epoch, and requiring date/clock columns locked auto-sync out of elapsed-time-only exports. Deltas come from the `tmcd` start timecode when *every* clip has one and from `creation_time` otherwise; the choice is all-or-nothing because the two are independent clocks sitting ~45 s apart on the HERO11 test footage, so a per-clip fallback would silently inject that gap. Timecode is preferred because `creation_time` is quantized to whole seconds (verified: 253.167 s vs 253.000 s between the two test clips). `timecode_delta` handles the midnight wrap, since a timecode is a time of day with no date. Every job gets the *same* `video_sync_sec` (copied from the base clip) — only `csv_sync_sec` varies per clip. Both halves of the base clip’s anchor are read from its own `ClipJob` (`base_csv_sync_sec`/`base_video_sync_sec` in `compute_auto_sync`), never passed in beside it: `AutoSyncParams` carries only `base_clip`. A separate copy invites the two to disagree — the GUI used to keep an editable “Video sync” box in the auto-sync row that the preview’s scrubbing never touched, so scrubbing to the sync frame and leaving the box at 0 anchored every clip to the wrong second. This is intentional (assumes every clip's manual sync point sits at the same video second, e.g. "film the dive computer for the first few seconds of every clip"), not a bug. `AutoSyncReport.warnings` flags clips landing outside the CSV's dive, which is how a clip from a *different* dive gets caught; it is computed before `csv_sync_sec` is clamped to 0, because the clamp would hide it.
- `yuv.rs` — `Yuv420Frame` (the planar 4:2:0 frames the pipeline moves between its two ffmpeg subprocesses) and `ColorRange`. The pipe used to carry `rgb24`, which cost two full swscale conversions per frame — out of the format the codecs already speak and straight back into it — twice the bytes, and a lossy chroma upsample/re-subsample on every frame. `ColorRange` is not cosmetic metadata: the overlay is drawn straight into the decoded planes, so its black/white points must match the picture's, or white text clips into illegal super-white on limited-range footage and reads as dull grey on full-range footage. GoPro records full range (`yuvj420p`/`color_range=pc`), so both cases occur. The decoder is asked for the source's *own* range so it hands the planes over with no conversion at all.
- `error.rs` — `CoreError`/`CoreResult`; error message text is part of the CLI's user-facing contract — preserve wording when refactoring.

## Processing modes

Two mutually exclusive `OutputMode`s selected by `--mode`/GUI toggle:
- **Overlay** (default): burns telemetry into pixels via full decode→draw→encode; supports `--codec`, `--resolution` (downscale) and `--show-graph` (depth-profile mini-graph).
- **Subtitles**: writes a soft `mov_text` subtitle track (+ `.srt` sidecar) via lossless remux; no re-encode, no codec/graph/resolution options (subtitles can't render a graph, and resizing would mean re-encoding, defeating the mode).

## GUI architecture (`dive_overlay_gui/src/main.rs`)

Single `App` struct driving an egui immediate-mode UI. `run_worker` takes one `WorkerConfig` struct rather than positional arguments — keep new settings inside it.

The sync preview is deliberately two-staged: the scrub buttons move `video_sync_sec` and re-seek (`refresh_preview_frame`), the CSV sync text field only redraws the info box (`redraw_preview_overlay`). `PreviewState` therefore caches both the *un-overlaid* frame and the parsed CSV samples, so a keystroke costs neither an ffmpeg seek nor a CSV re-parse; `try_render_preview` is the only path that pays for both. The CSV sync field edits a buffer (`csv_sync_edit`) and writes back to the clip only once the value parses, so half-typed input like `1:` doesn't clobber it.

Long-running work (video processing, GitHub update check) runs on background `std::thread::spawn` threads that communicate back via `mpsc` channels (`WorkerEvent::{Log,Progress,Fps,Encoder,Done}` for processing, a separate channel for `update_check::UpdateStatus`), with `ctx.request_repaint()` used to wake the UI thread. Cancellation goes through a shared `Arc<AtomicBool>` cancel flag threaded down into `dive_overlay_core::pipeline`.
